# HASE MCP optional OAuth — architecture verification and decision gate

Status: **STOP-AND-REPORT before implementation** (2026-10-07). No OAuth code or configuration has been added.

## Verified current architecture

- One dedicated Uvicorn listener serves the MCP SDK's stateless Streamable HTTP app on `0.0.0.0:<port>/mcp`. The listener has no TLS and currently has no real OAuth authorization server. Its required SDK `issuer_url` is deliberately a nonfunctional `.invalid` placeholder (`providers/mcp/transport.py`, `providers/mcp/__init__.py`).
- A new MCP Bridge subentry receives one high-entropy static credential. The token is shown once; HA persists its HMAC-SHA256 verifier and display suffix, while the per-installation HMAC secret lives in `.storage/hase.mcp_secret` (`providers/mcp/config_flow.py`, `credentials.py`, `secret_store.py`). Reconfiguration preserves it unless explicitly regenerated.
- On each HTTP request the SDK calls `HaTokenVerifier.verify_token`. HASE resolves the verifier against the current immutable Bridge publication, refreshes that Bridge, and returns an SDK `AccessToken` containing the Bridge entry/subentry IDs and generation. The client does not supply its Bridge ID (`transport.py`, `runtime.py`).
- `tools/list` and `tools/call` resolve that authenticated identity into a request-scoped generation lease. The Bridge snapshot supplies one Spellbook, speaking area, language and independent action/query `AreaPolicy`; live HA target exposure and Expert rules remain in the existing executor/projection. Generation checks prevent stale publication and pre-side-effect work after a Bridge change (`transport.py`, `core/mcp_bridge_context.py`, `core/mcp_execution.py`, `runtime.py`).
- There is no separate HASE user/client principal registry or tool-specific permission table. **The Bridge is the operative MCP principal.** `AccessToken.scopes=[]` for static credentials. MCP tool `readOnlyHint` is advisory and cannot authorize a call (`docs/en/security.md`, `core/mcp_projection.py`).
- Existing normative documentation describes static Bearer as the only mechanism and LAN/reverse-proxy deployment as the security boundary (`docs/HASE-MCP.md`, `docs/en/security.md`). These contracts must be updated only after an OAuth design is approved and implemented; existing Bridge tokens/config entries must remain valid.

## Standards and available integration point

The MCP Python SDK's resource-server hook is already in use: one `TokenVerifier` receives the bearer value and returns an `AccessToken`. Its `AuthSettings` supports a real `issuer_url`, `resource_server_url`, scopes and resource validation. The [SDK authorization guide](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/run/authorization.md) describes the MCP server as a resource server and an external identity provider as the authorization server; the SDK publishes [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728.html) protected-resource metadata from those settings. [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html) defines audience restriction for the public MCP resource URL. [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html) defines introspection of an opaque access token's active state, scope, client and expiry.

Thus OAuth can join static Bearer at the existing verifier and then use the same Bridge lease, Spellbook and authorization path. No second capability system is structurally necessary. **Token acceptance alone is not sufficient:** the OAuth identity must be bound to a specific Bridge, the resource/audience must be checked, and OAuth scope must only restrict the Bridge's existing permissions.

## Decisions required before safe implementation

| Decision | Option A — external authorization server (recommended architecture) | Option B — HASE-hosted authorization server |
| --- | --- | --- |
| Issuance and client consent | A selected external OAuth provider issues and revokes tokens. HASE is only the resource server. | HASE implements/persists client registration, authorization, consent, codes, token issuance/refresh and revocation via a standards-compliant SDK provider. This is a substantially larger security and HA-storage surface. |
| Token validation | Prefer RFC 7662 introspection on every request, with bounded timeout and fail-closed response, if the chosen provider supports it. The provider's introspection client credentials become new HA secrets. JWT/JWKS would need a separate revocation decision. | HASE's own token store and revocation state become authoritative and must survive HA restart/reload. |
| Public endpoint | Configure the exact externally reachable HTTPS resource URL and HTTPS issuer. A trusted reverse proxy terminates TLS for HASE's existing local HTTP listener. The token audience is checked against that public resource. | Same public HTTPS resource requirement; HASE additionally exposes authorization endpoints. |
| Principal binding | Explicitly bind a verified issuer plus stable `sub` and/or `client_id` to a chosen existing MCP Bridge. No caller-supplied Bridge ID or arbitrary token claim may select one. Removal of the binding or Bridge revokes access on the next request. | Same binding requirement, unless the user explicitly chooses a different principal model. |
| Scope | Choose a precise scope vocabulary. A Bridge-level scope can gate all tools of that Bridge while its existing Spellbook/AreaPolicy remains the narrower authority. Read/query versus action scopes would require a proven classification for combined and text-only spells; `readOnlyHint` cannot serve as that proof. | Same scope decision. |

The repository and standards do not choose an authorization-server operator/provider, a public HTTPS resource identifier, the OAuth identity-to-Bridge binding rule, or a scope vocabulary. Home Assistant's published OAuth client/integration helpers address integrations obtaining tokens for another service; its [Authentication API](https://developers.home-assistant.io/docs/auth_api/) describes HA user tokens, but no current HASE contract establishes those tokens as audience-restricted MCP Bridge credentials. Treating them as such would be an unsupported security assumption.

## Proposed narrow first implementation once decided

Keep static Bearer entirely unchanged. For an explicitly configured external issuer: publish truthful protected-resource metadata; validate an access token's active status, expiry, issuer, intended MCP resource and required scope through the chosen standard verifier; map its verified identity to one configured Bridge; return the same Bridge identity/generation claims used by static Bearer; enforce scope as an additional restriction before `tools/list` and `tools/call`; continue to use the existing generation lease and executor. Never log token values or return them in diagnostics. A revoked token must fail the next request, including on an already-connected stateless MCP client. TLS for the public URL and bounded introspection failures are deployment and runtime invariants.

No implementation or test claim is made yet. The static Bearer path and all Phase 2 changes remain untouched.

## Follow-up decision and Home Assistant verification (2026-10-07)

The user chose Home Assistant Auth as the sole desired OAuth base, one HA `user_id` per MCP Bridge and vice versa, multiple concurrent client tokens for that user, and no new tool/query/action scopes. Static Bearer must remain parallel. The current HA Auth implementation and the installed MCP Python SDK 2.2.0 were checked specifically against that design. **Implementation remains stopped because of one concrete token-audience incompatibility.** This is a technical finding, not a request to choose an external provider.

| Requirement | Verified Home Assistant / SDK behavior | Result |
| --- | --- | --- |
| Authorization code, PKCE, client identity and redirect | HA exposes `/auth/authorize` and `/auth/token`, advertises Authorization Server Metadata with `authorization_endpoint`, `token_endpoint`, `revocation_endpoint`, `client_id_metadata_document_supported` and S256 PKCE. Its login flow checks URL-based `client_id` and redirect URI via IndieAuth. | Potentially usable for client login; live client interoperability would still need testing. [HA metadata source](https://github.com/home-assistant/core/blob/dev/homeassistant/components/auth/login_flow.py), [HA Auth API](https://developers.home-assistant.io/docs/auth_api/). |
| Stable user, access-token expiry and revocation | `hass.auth.async_validate_access_token(token)` verifies the HA JWT and returns its parent refresh-token object only while it exists and its user is active. The parent exposes the stable user; removing the refresh token invalidates its access tokens. HA's `/auth/revoke` handles refresh-token revocation. | A custom component could validate HA identity in process without an HTTP loopback. [HA AuthManager](https://github.com/home-assistant/core/blob/dev/homeassistant/auth/__init__.py), [HA token/revoke endpoints](https://github.com/home-assistant/core/blob/dev/homeassistant/components/auth/__init__.py). |
| Discovery / public resource | The MCP SDK `AuthSettings` and resource-server middleware can publish RFC 9728 metadata and issue 401 challenges when configured with a real public `resource_server_url` and issuer. HASE presently uses a placeholder issuer and no public resource URL. HA's AS metadata is on the HA origin; HASE MCP is on a separate configurable listener. | A small metadata/config adapter is feasible, with explicit HTTPS URLs and proxy routing. This does not fix the token below. [MCP SDK auth guide](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/run/authorization.md). |
| **MCP access-token audience** | The [MCP 2026-07-28 Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) requires clients to send `resource` on authorization **and token** requests and resource servers to accept only tokens issued for their canonical MCP resource. HA's current `async_create_access_token` signs exactly `iss` (HA refresh-token ID), `iat`, and `exp`; it contains no `aud` or resource claim. Its authorization-code and refresh handlers create ordinary HA API tokens from `client_id` and do not carry a requested `resource` into issuance. | **Incompatible.** `async_validate_access_token` proves that HA accepts the token for HA; it cannot prove the token was issued for HASE's separate MCP resource. Supplying an MCP URL in SDK metadata or comparing HA `client_id` with a Bridge does not turn a general HA token into an audience-bound MCP token. [HA JWT creation/validation](https://github.com/home-assistant/core/blob/dev/homeassistant/auth/__init__.py), [HA token handler](https://github.com/home-assistant/core/blob/dev/homeassistant/components/auth/__init__.py), [MCP token handling](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization). |

The `client_id` is the OAuth **client** identifier, not the HASE MCP resource/audience. HA's one-to-one `user_id` to Bridge mapping would be straightforward after valid authentication, but it is not a substitute for resource-specific issuance. The existence of HA's own RFC 9728 metadata for the HA origin likewise does not bind HA tokens to HASE's separately addressed MCP endpoint. No Nabu Casa identity-provider assumption is needed or made.

### Smallest technically clean adapter and cost

The cleanest solution without an external provider is a **Home Assistant Core capability**: support RFC 8707 `resource` for authorization-code and refresh grants, issue access tokens carrying an audience for the exact public HASE MCP URL, and expose that audience in an established validation API. HASE would then add only its resource metadata/config and `user_id`↔Bridge binding, validate `aud` and token lifecycle per request, and reuse the existing Bridge generation lease. This is a change to HA's authorization-server contract, outside this custom component; it needs HA Core implementation, review, release/version gating and interoperability tests. A HASE-only metadata or verifier adapter cannot produce the missing issuance fact.

A HASE-managed token exchange/broker could accept a HA login and mint separate MCP-audience tokens, but would become an authorization server responsible for secure code/token issuance, refresh, revocation, client/redirect policy, persistence and discovery. That is the substantial second security system the user explicitly excluded. Accepting generic HA API tokens based only on their valid user ID would be smaller code but would violate the MCP audience requirement and enable a token intended for HA to be replayed at HASE MCP.

### Alternatives and recommendation

1. **Recommended:** keep static HASE Bearer for now, including behind a correctly secured HTTPS reverse proxy for remote use, and pursue/verify HA Core support for resource-bound access tokens. Resume the chosen 1:1 Bridge binding after HA exposes a supported audience-aware issuance and validation contract.
2. If optional OAuth is needed before that HA capability exists, use a standards-compliant external authorization server that issues audience-bound MCP tokens. The user rejected making one a prerequisite, so this is a product-direction alternative, not an implementation performed here.
3. A HASE-owned authorization server is technically possible but violates the requested architecture and adds significant long-term security and maintenance responsibility.

No OAuth config field, metadata endpoint, token verifier branch or test was added. The existing static Bearer path and previously modified Phase 2 files remain as they were. This verification used current upstream HA source and docs; Home Assistant is not installed in the local test venv, so no live HA OAuth flow was asserted.
